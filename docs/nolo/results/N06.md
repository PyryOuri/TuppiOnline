# N06 — Exact caching: correct, and not worth keeping

Task status: **COMPLETE**. Scientific outcome: **NO USEFUL SPEED GAIN**.
Correctness passed on every matched position; the cost target was missed in the
wrong direction. The uncached search stays the default and N07 proceeds on it.
Date: 2026-09-05.

## The question and the answer

Can exact repeated-subproblem caching reduce engine transitions while preserving
root values and valid plans? It preserves them exactly. It does not reduce
transitions — it **increases** them by 6.3% across the matched set, and is slower
in wall time too.

## What was built

[`src/tuppi_nolo/cache.py`](../../../src/tuppi_nolo/cache.py) adds a bounded memo
and a two-pass search selected by passing a `SecurityCache` to `solve_security`.
The plain path is untouched and remains the independent reference.

The key is history-independent and deliberately conservative: root information
key, objective, control model, starting score, current actor, the public partial
trick in order, accumulated team tricks, the controlled seat's remaining hand
**in its own order**, and the complete set of feasible remaining allocations —
each seat's cards sorted because unseen order is not observable, the set sorted
so enumeration order cannot split a key. Suit lengths and the union of unknown
cards are never used, and no component names a single hidden world. Two positions
sharing that key have the same cards in the same hands with the same turn and
totals, so the reachable game, and therefore the value, is identical.

Only **values and optimal action sets** are cached, never plans. Plan keys hash
the whole public history, so a borrowed plan would name keys that do not exist
here. The value is history-independent; the choice among equally valued actions
is not, because the v2 ranking reads the observation. Pass two therefore rebuilds
the plan against the current history and re-applies the tie rule there, which is
what keeps baseline ties exactly where the plain search puts them.

## Correctness — PASS

Comparison set frozen before any timing: A/B/C plus every decision with two or
more legal actions and at most three remaining tricks in the first 32 deals of
seed `nolo-info-dev-v1`, forced NOLO, all-v2 play. **226 positions**, listed in
`work/nolo/n06/positions.json`.

| | |
| --- | ---: |
| solved completely by both paths | **179** |
| differences in root values or action | **0** |
| plans rejected by the N03 verifier | **0** |
| unresolved by both (budget) | 46 |
| solved only by the cached path | 1 |
| solved only by the plain path | 0 |

The one position solved only by the cached path (deal 12, seat 1, trick 10) is a
coverage observation and is **not** folded into any speed figure: the plain path
returned `SEARCH_BUDGET` there, so it produced no value to disagree with. The
comparison script initially flagged it as a mismatch, which was the script being
too broad rather than a real discrepancy — the endpoint is about positions both
paths resolve.

## Cost — FAIL

Aggregate engine transitions on the 179 identically solved positions:

| | plain | cached | change |
| --- | ---: | ---: | ---: |
| all matched | 1,129,304 | 1,200,576 | **−6.3%** |
| 2 tricks remaining (n=116) | 167,186 | 218,895 | −30.9% |
| 3 tricks remaining (n=63) | 962,118 | 981,681 | −2.0% |

The cache cost more on **168 of 179** positions. Target was at least 20% fewer;
the result is 6.3% more.

Wall time, reported separately and never conflated with the work counts —
medians of three repeats:

| fixture | plain | cached | change |
| --- | ---: | ---: | ---: |
| A | 71,460 ms | 65,527 ms | +8.3% |
| B | 957 ms | 1,410 ms | −47.3% |
| C | 13,761 ms | 17,376 ms | −26.3% |

Matched-set median across the 226-position run: plain 2,603 ms, cached 3,430 ms.

## Why it loses

The overhead is structural, not an implementation detail that tuning would fix.
The memoised path is two passes, and the second one still visits **every
opposition branch**, because the plan must name an action at each own key those
branches can reach. Only the own branching is saved. That is a fixed cost paid on
every position, while the hits it has to repay are scarce: within three tricks
there are few genuine transpositions, since a distinct play order generally
leaves a distinct partial trick, distinct accumulated totals, or distinct
remaining hands, and any of those separates the key.

The depth trend is the clearest evidence. At two remaining tricks the overhead
dominates (−30.9%); at three it nearly washes out (−2.0%) but still does not turn
positive. Amortisation would need trees deeper than the frozen three-trick budget
allows, which is outside this task.

A caveat on the key: it is deliberately conservative, and a coarser one might hit
more often. The task's instruction was to retain the finer key wherever a coarser
one's sufficiency could not be explained, and no coarsening was found that could
be justified rather than merely tried. A second optimisation was not permitted
here in any case.

## Bounded behaviour, and a bug this found

A full cache stops storing rather than starts guessing. The first implementation
crashed in that state: pass two could reach an own node whose value had been
computed but refused storage, and it raised. Running out of memo space is allowed
to cost time and is never allowed to cost an answer, so such a node is now
recomputed. The test using `max_entries=5` exercises it and asserts the answers
match the uncached path exactly.

Counters are explicit — hits, misses, lookups, stores, rejections when full,
entries against the bound — and a spent budget still yields `SEARCH_BUDGET` with
no root values, no action and no certificate on the cached path.

## Consequence

Keep the simple uncached default, which is what `solve_security` does without a
cache argument. The cached path stays available and correct, so N07 may use it —
it passed correctness — but there is no reason to. The 20% figure was a
prospective engineering threshold, not a prediction, and it was not met.
